RAGDom · Déploiement web · Single-origin FastAPI

Déployer RAGDom : du poste local au web

RAGDom est une bibliothèque numérique scientifique local-first avec version web complète. Un même processus FastAPI sert l'interface compilée ET l'API (single-origin, zéro CORS inter-origines). Ce guide couvre les trois façons de l'exécuter — en IDE pour développer, en build local pour la production sur poste, et en ligne sur Render.com via Docker — puis détaille chaque variable de configuration et le dépannage réel.

Version V3.12 FastAPI + sci-engine Python 3.9+/3.11 · Node 20 SQLite · FTS5 + sqlite-vec

01Vue d'ensemble & architecture

Le postulat central est le single-origin : au démarrage, backend/main.py monte les routes /api/* puis, si le dossier frontend/dist existe (ou si RAGDOM_UI_DIST pointe vers un build), il monte ce dossier sur / avec un fallback SPA : toute URL sans extension qui n'est pas une route API renvoie index.html. Une seule URL sert donc l'application entière — pas de VITE_API_URL, pas de CORS inter-origines en production.

# backend/main.py — montage single-origin (extrait fidèle)
_DIST_DIR = os.environ.get("RAGDOM_UI_DIST") or .../frontend/dist
if os.path.isdir(_DIST_DIR):
    class _SPAStaticFiles(StaticFiles):
        async def get_response(self, path, scope):
            try: return await super().get_response(path, scope)
            except 404:
                if "." not in dernier_segment:          # route SPA
                    return index.html
    app.mount("/", _SPAStaticFiles(directory=_DIST_DIR, html=True))

Les routes /api/* sont montées avant le mount statique : elles gardent la priorité. Le backend expose 60 routes réparties sur 7 routers (system, library, search, pipeline, llm, curriculum, auth).

Schéma des composants

Trois modes d'exécution couverts par ce guide : §02 IDE le frontend Vite (5173) et le backend (8000) tournent séparément, Vite proxie /api vers le backend ; §03 build local le frontend est compilé dans dist/ et servi par FastAPI, une seule origine http://localhost:8000 ; §05 Render l'image Docker fait la même chose en ligne.

02Local via IDE (développement)

Prérequis

Python

3.9+ (cible 3.11). Le code évite toute syntaxe 3.10+ (voir config.py). Le lanceur crée un venv backend/.venv.

Node.js

Node 20 (aligné sur l'étage build du Dockerfile node:20-alpine). Fournit npm pour le frontend Vite 5 et les scripts racine.

Installation initiale & lancement unifié

Le package.json racine orchestre tout via scripts/dev-backend.mjs (lanceur multiplateforme Windows/Linux/macOS). Deux commandes suffisent :

# À LA RACINE du dépôt
npm install          # concurrently (dépendance de lancement)
npm run setup        # frontend: npm install  +  backend: crée .venv, installe requirements.txt
                     #   puis post-install obligatoire : opencv-python-headless + numpy 1.26.4
npm run dev          # lance API + UI en parallèle (concurrently)

Ce que npm run dev déclenche réellement, d'après le lanceur :

  • venv auto-détecté : le script cherche le Python dans backend/.venv, backend/venv, puis .venv/venv à la racine. Absent → message « lancez d'abord : npm run setup ».
  • port libre automatique : il part de BACKEND_PORT (défaut 8000) et teste jusqu'à +19 ; s'il est occupé, il bascule (« Port 8000 occupé → bascule sur 8001 ») et exporte le port choisi pour que le proxy Vite le suive.
  • double processus : concurrently lance node scripts/dev-backend.mjs (uvicorn avec --reload) et npm --prefix frontend run dev (Vite). Le dev-server Vite écoute sur 5173 et proxie /api vers http://localhost:${BACKEND_PORT}.

Première utilisation : créer le compte

Le login se fait par NOM D'UTILISATEUR, pas par email. C'est explicite dans routes_auth.py : identifiant de 3 à 64 caractères (lettres, chiffres, _ - . — sans espaces ni accents) + mot de passe de 8 caractères minimum. Le hachage est scrypt (stdlib, sel aléatoire par compte), aucune dépendance hors whitelist. La session émise (12 h glissantes) sert de jeton Bearer.
  • Ouvrez l'UI, allez sur /login — l'écran de création apparaît tant qu'aucun compte n'existe.
  • En local, la création du premier compte est libre (postulat Local-First : tant qu'aucun compte n'existe et qu'aucun RAGDOM_AUTH_TOKEN n'est défini, l'administration reste ouverte).
  • Dès qu'un compte existe (ou qu'un jeton env est défini), les routes d'administration exigent une session valide (401 sinon).

Lancer le backend seul

Pour travailler sur l'API sans le dev-server Vite :

cd backend
python main.py            # ou : python -m uvicorn main:app --reload

main.py et config.py déduisent tous les chemins de l'arborescence du projet (racine = parent de backend/) : sources/, databases/, pipeline_set/, models/, engines/, et backend/ragdom_config.sqlite. Le .env est donc optionnel — il ne sert qu'à personnaliser. Si frontend/dist n'existe pas encore, seul l'API répond (attendu en mode IDE).

03Local après build (production locale)

Pour obtenir le comportement single-origin sur votre poste — une seule URL qui sert tout, comme en ligne — compilez le frontend puis lancez le backend :

1

Compiler l'interface

cd frontend
npm run build     # tsc -b && vite build → génère frontend/dist/

Le build TypeScript strict (tsc -b) précède Vite : une erreur de type fait échouer le build.

2

Lancer le backend (il sert l'UI compilée)

cd backend
python main.py

Au démarrage, main.py détecte frontend/dist et affiche [RAGDom] UI servie en single-origin depuis …. Tout est alors accessible sur une seule origine :

http://localhost:8000  →  l'UI sur /, les routes SPA (ex. /library), et l'API sur /api/*.

RAGDOM_UI_DIST (optionnel). Par défaut, FastAPI cherche <racine>/frontend/dist. Pour servir un build situé ailleurs (dossier partagé, artefact CI), définissez RAGDOM_UI_DIST=/chemin/vers/dist — le mount statique s'appuie sur ce dossier à la place.

Vérifier

curl http://localhost:8000/api/system/health
# → {"status":"ok","version":"3.5","vector_engine":"sqlite-vec",
#    "vector_engine_status":…, "force_sqlite_vec":false, "readonly":false, …}

04Configuration .env exhaustive

Toute la configuration passe par des variables d'environnement, lues par backend/config.py (chemins, serveur, pipeline) et directement par le moteur / main.py / db/connection.py pour les options web. Le fichier backend/.env est versionné, pré-rempli et sans secret : chaque ligne y est commentée (le # = valeur par défaut active). On décommente uniquement ce que l'on veut changer.

Règle d'or des secrets. Le dépôt étant public, ne jamais écrire de secret dans .env (jeton d'admin, clés LLM). Les secrets vont dans l'environnement de l'hébergeur (Render → Environment). Les variables purement locales (chemins, ports) peuvent rester dans .env sans risque.

Sécurité web config.py + access_policy.py

VariableDéfautSémantique / quand la changer
RAGDOM_READONLYfalseBooléen. true = mode consultation : les routes d'administration n'existent pas (404) — seules les lectures (library, search/ask, system-read, auth) répondent. Idéal pour une bibliothèque publique en lecture seule.
RAGDOM_AUTH_TOKEN(vide → None)Secret. Si défini, les routes d'administration exigent Authorization: Bearer <jeton> (401 sinon). Sur le web il rend aussi /api/auth/setup protégé : le premier visiteur ne peut pas s'approprier l'instance. Obligatoire en ligne si READONLY=false.
RAGDOM_ALLOW_REVEALtrueBooléen. Autorise la lecture en clair d'une clé LLM via POST /api/llm/keys/{id}/reveal. true par défaut (postulat local). Mettre false sur tout déploiement web → la route renvoie 403.
RAGDOM_ASK_RATE_PER_MIN0Entier. Quota de POST /api/search/ask par IP et par minute (fenêtre glissante 60 s en mémoire process). 0 = désactivé (défaut local). Mettre > 0 en ligne (ex. 6-12) pour protéger vos quotas LLM (429 au dépassement).
RAGDOM_SEED_LLM_KEYS(vide)Secret. Seed idempotent des clés LLM au démarrage (relu à chaque init_config_db()). Indispensable sur disque éphémère où la config repart de zéro. Format : entrées séparées par virgules ou retours ligne, chacune provider:clé ou provider:clé:modèle. Chaque entrée absente est insérée et le provider activé. Ex. : gemini:VOTRE_CLE:gemini-2.5-flash,groq:VOTRE_CLE.
RAGDOM_PUBLISHED_DBS<racine>/databases_publieesDossier de bases pré-ingérées. Au démarrage, chaque .sqlite présent y est copié vers DATABASES_DIR s'il est absent (copie non destructive, jamais d'écrasement) — la bibliothèque renaît identique à chaque réveil du disque éphémère.
Booléens : RAGDOM_READONLY, RAGDOM_ALLOW_REVEAL, RAGDOM_LOW_MEMORY, RAGDOM_OFFLINE, RAGDOM_FORCE_SQLITE_VEC se comparent à "true" (insensible à la casse). RAGDOM_AUTH_TOKEN vide vaut None (aucun contrôle par jeton env). RAGDOM_VLM_PAGE_OCR est une exception : seul false désactive.

5

Redéployer — l'autodeploy peut être inopérant

Sur ce service, l'autodeploy sur push n'est pas fiable : après un git push, le redéploiement doit souvent être déclenché à la main. Deux voies :

A. Bouton Manual Deploy

dashboard.render.com/web/srv-…
Service · ragdom
Manual Deploy ▾Deploy latest commit / Clear cache & deploy

B. Via l'API Render (curl)

curl -X POST \
  -H "Authorization: Bearer $RENDER_API_KEY" \
  -H "Accept: application/json" \
  https://api.render.com/v1/services/<VOTRE_SERVICE_ID>/deploys
# → renvoie un objet deploy (dep-…) ; on peut ensuite poller son statut.

<VOTRE_SERVICE_ID> est l'identifiant srv-… visible dans l'URL du service. RENDER_API_KEY se crée dans Account Settings → API Keys. Ne jamais committer cette clé.

Contraintes du plan Free & parades réelles

512 Mo RAM

L'encodeur d'embeddings ne tient pas. Parade : RAGDOM_LOW_MEMORY=true → recherche BM25 seule en ligne, aucune régression fonctionnelle sur la consultation.

Veille après 15 min

Le service s'endort sans trafic ; le premier accès suivant met ~1 min à réveiller l'instance. Parade : accepter la latence, ou pinger périodiquement.

Disque éphémère

Au redémarrage, le disque repart de l'image. Parades câblées (ci-dessous) : corpus dans l'image, bases pré-ingérées seedées au boot, clés LLM re-seedées.

Comment RAGDom survit à un disque éphémère

  1. Corpus embarqué dans l'image. Le Dockerfile fait COPY sources/ sources/ et pose SOURCES_DIR=/app/sources : les PDF du dépôt font partie de l'image, persistants aux redémarrages.
  2. Bases pré-ingérées via release GitHub. Les .sqlite volumineux (> 100 Mo, interdits dans le dépôt) sont téléchargés au build depuis une release GitHub vers databases_publiees/ : 
    # Dockerfile (extrait)
RUN mkdir -p databases_publiees \
 && curl -fsSL -o databases_publiees/<base>.sqlite \
    https://github.com/<vous>/RAGDom/releases/download/<tag>/<base>.sqlite \
 || echo 'bases publiées non téléchargées (release absente) — démarrage à vide.'
    Puis, au démarrage, main.py copie tout .sqlite de databases_publiees/ vers DATABASES_DIR s'il est absent → la bibliothèque renaît pré-chargée à chaque réveil.
  3. Clés LLM re-seedées à chaque boot via RAGDOM_SEED_LLM_KEYS (voir §04) : la config repart de zéro, mais les clés sont réinsérées et le provider réactivé automatiquement.

06Docker générique (tout hébergeur)

La même image tourne sur n'importe quel hébergeur de conteneurs (VPS, Fly.io, Railway, Koyeb, Coolify…) ou en local avec Docker installé.

1

Construire l'image

docker build -t ragdom .

Étage 1 (node:20-alpine) : npm run build. Étage 2 (python:3.11-slim) : installe la whitelist requirements.txt (llama-cpp-python exclu de l'image web), applique le post-install OpenCV headless, copie le backend, les moteurs, sources/, les bases publiées et dist/.

2

Lancer le conteneur

docker run -p 8000:8000 \
  -e RAGDOM_AUTH_TOKEN=VOTRE_JETON \
  -e RAGDOM_ALLOW_REVEAL=false \
  -e RAGDOM_ASK_RATE_PER_MIN=6 \
  -e RAGDOM_LOW_MEMORY=true \
  -e RAGDOM_SEED_LLM_KEYS=gemini:VOTRE_CLE:gemini-2.5-flash \
  -v ragdom_data:/data \
  ragdom
# → http://localhost:8000 sert l'UI ET l'API (single-origin).

Le volume /data est optionnel mais recommandé hors plan gratuit : il persiste databases/, pipeline_set/, models/ et ragdom_config.sqlite entre les redémarrages (chemins déjà posés par le Dockerfile sous /data). Sans volume, on retombe sur le modèle « bases publiées seedées au boot » du §05.

07Publier son propre corpus

Le workflow réel pour mettre en ligne vos bibliothèques, sans ingérer sur le serveur :

1

Ingérer localement

Faites tourner le pipeline sur votre poste (idéal : plein d'RAM, embeddings actifs). La bibliothèque produite est un fichier .sqlite unique dans databases/.

2

Choisir le canal de publication selon la taille

< 100 Mo

Dépôt direct

Déposez le .sqlite dans databases_publiees/ et committez-le. Au prochain build/boot, il sera seedé vers DATABASES_DIR.

> 100 Mo

Release GitHub

GitHub refuse les fichiers > 100 Mo dans le dépôt. Publiez le .sqlite en asset de release (assets jusqu'à 2 Go).

3

Référencer la release dans le Dockerfile

Ajoutez (ou adaptez) une ligne curl dans le bloc bases publiées du Dockerfile, pointant vers l'URL de téléchargement de votre asset :

RUN curl -fsSL -o databases_publiees/<ma_base>.sqlite \
    https://github.com/<vous>/RAGDom/releases/download/<tag>/<ma_base>.sqlite

Au build, l'asset est téléchargé dans l'image ; au démarrage, main.py le copie vers DATABASES_DIR s'il est absent. La copie est non destructive : une base déjà présente n'est jamais écrasée.
